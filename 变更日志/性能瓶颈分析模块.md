# 性能瓶颈分析模块实现日志

## 1. 目标
为了满足路线图第四周关于“性能瓶颈分析”的要求，我们需要一套工具来量化后端服务的 CPU 使用率和响应延迟，特别是针对 RAG 和数据库操作。

## 2. 工具选型
我们在 Windows 环境下选择了以下工具组合：

| 工具 | 用途 | 选择理由 |
| :--- | :--- | :--- |
| **py-spy** | CPU 采样分析 | 对 Python 进程进行非侵入式采样，生成火焰图，开销低。支持 Windows。 |
| **Locust** | 负载生成 | 用 Python 编写压测脚本，模拟真实用户行为（并发登录、对话）。 |
| **PowerShell** | 自动化编排 | 编写 `run_analysis.ps1` 脚本，一键完成环境清理、服务启动、压测和分析。 |


## 3. 使用指南与测试范围

### 3.1 如何使用

**前置要求**：
- Windows 系统
- **管理员权限**运行 PowerShell (因 `py-spy` 需要读取进程内存)
- 已安装 `conda` 环境 `fastapi_env`

**运行命令**：
```powershell
# 在项目根目录下运行
./server-python/performance/run_analysis.ps1
```

**运行过程**：
1. 脚本会自动清理端口 8000 的旧进程。
2. 启动服务器并等待 20秒 预热。
3. 启动压测和录制，持续 60秒。
4. 自动生成火焰图 `server-python/performance/profile.svg`。

### 3.2 测了什么？ (测试范围)

我们在 `server-python/performance/locustfile.py` 中进行了针对性的调整，**100% 专注于 Agent 智能问答**，排除了其他干扰：

1.  **核心业务重负载 (权重 100%)**
    -   **行为**: 持续发送 RAG 对话请求 (`POST /api/chat/stream`)
    -   **问题库**: 随机抽取真实健身问题（如“如何增肌”、“制定计划”）。
    -   **测试目标**: 
        -   **全链路性能**: 涵盖 [Prompt 组装] -> [向量检索] -> [豆包大模型调用] -> [流式响应] 的完整过程。
        -   **排查瓶颈**: 能够清晰地看到是大模型回复慢，还是我们自己的 Python 代码处理慢。

2.  **已禁用模块**
    -   ❌ `/health` (心跳检测)
    -   ❌ `/api/profile` (数据库读写)

### 3.3 结果解读：如何验证优化成功？

我们需要结合**定性**与**定量**两套标准来验证。

#### A. 定量指标 (看 CSV 报表)
脚本运行结束后，会生成 `server-python/performance/locust_report_stats.csv`。重点关注以下两列，它们是衡量性能的**金标准**：

1.  **Average Response Time (平均响应时间)**
    -   **含义**: 用户从发消息到收到回复平均要等多久。
    -   **判断**: 数值**越小越好**。
    -   *示例*: 如果从 `3500ms` 降到了 `1200ms`，说明优化效果显著。

2.  **Requests/s (RPS, 吞吐量)**
    -   **含义**: 服务器每秒能同时处理多少个并发对话。
    -   **判断**: 数值**越大越好**。
    -   *示例*: 从 `0.5 RPS` 提升到 `2.0 RPS`，意味着并发能力翻了 4 倍。

#### B. 定性分析 (看火焰图)
打开 `server-python/performance/profile.svg`，只需关注三点：

1.  **看宽度 (Width = Time)**
    -   **越宽越慢**：格子的宽度代表该函数在 60 秒内占用的时间比例。
    -   **优化策略**：**总是优先优化最宽的那些块**。如果优化后，某个原本很宽的块（如 `compute_embedding`）变窄了，说明它不再是瓶颈。

2.  **看层级与行号**
    -   **格式**: `函数名 (文件名:行号)`，末尾数字精确指向代码行数。
    -   **实战**: 看到 `get_relevant_documents (vector_store.py:45)` 很宽，直接去改那里！

## 4. 实现逻辑

### 4.1 自动化脚本 (`run_analysis.ps1`)
为了解决手动操作繁琐且容易出错的问题（如忘记关闭旧进程、端口冲突），我们实现了一个全自动脚本：

1.  **环境清理**：启动前强制查找并终止所有占用 `8000` 端口的进程，防止代码残留。
2.  **服务启动**：后台启动 `FastAPI` 服务。
3.  **智能等待**：
    -   循环检测端口是否就绪（最多 30s）。
    -   **预热等待**：服务就绪后再等待 20s，跳过模块加载和数据库初始化的 CPU 消耗，只录制稳定运行时的流量。
4.  **精准定位**：使用 WMI 过滤（`Name='python.exe'` 且命令行包含 `main.py`），精确定位到 Python 解释器进程，避开 Conda 的 Wrapper 进程。
5.  **同步压测**：在 `py-spy` 录制的同时启动 `Locust` 无头模式进行高并发请求。
6.  **资源回收**：分析结束后自动关闭服务器进程。

### 4.2 负载模拟 (`locustfile.py`)
为了产生真实的负载，我们定义了 `GymUser`：
-   **唯一身份**：每次启动生成 UUID 用户名，确保注册/登录 100% 成功，避免压测变成“400 错误测试”。
-   **混合场景**：
    -   `health_check` (权重 5): 模拟心跳检测。
    -   `view_profile` (权重 3): 读操作。
    -   `chat_rag` (权重 2): **重负载操作**，触发 LLM 调用和向量检索。

## 5. 代码变更对比

### 5.1 认证模块 (`auth.py`)
在压测过程中发现旧的 `passlib` 库在生成哈希时与新版 `bcrypt` 不兼容，导致大量 500 错误。我们进行了重构：

**变更前 (使用 passlib):**
```python
from passlib.context import CryptContext
pwd_context = CryptContext(schemes=["bcrypt"], deprecated="auto")

def get_password_hash(password: str) -> str:
    return pwd_context.hash(password[:72])

def verify_password(plain_password: str, hashed_password: str) -> bool:
    return pwd_context.verify(plain_password[:72], hashed_password)
```

**变更后 (直接使用 bcrypt):**
```python
import bcrypt

def get_password_hash(password: str) -> str:
    # 显式处理 bcrypt 的 72 字节限制
    pwd_bytes = password.encode('utf-8')
    if len(pwd_bytes) > 72:
        pwd_bytes = pwd_bytes[:72]
    
    salt = bcrypt.gensalt()
    return bcrypt.hashpw(pwd_bytes, salt).decode('utf-8')

def verify_password(plain_password: str, hashed_password: str) -> bool:
    plain_password_bytes = plain_password.encode('utf-8')
    if len(plain_password_bytes) > 72:
        plain_password_bytes = plain_password_bytes[:72]
        
    hashed_password_bytes = hashed_password.encode('utf-8')
    return bcrypt.checkpw(plain_password_bytes, hashed_password_bytes)
```
